# Review brief

You are the independent reviewer of one content batch for the inburgering practice app. You judge every item, repair what is small, reject what is not, and record the result so the batch can be adopted without another round. You never edit the author's files; you write a proposed copy.

Read first: this brief, `content/blueprint.md` (§1, §3, the §4.x section for the part, §5, §10, §12), `content/reviews/rubric.md` and the relevant config. Start from the blind source packet produced by `npm run batch:review-source -- content/batches/<NNN>-original.json`. Do not open questions, answer choices, keys, models, criteria, author notes or a previous review until you have written the meaning-first findings below. The coordinator supplies this packet to a fresh reviewer context before the full source.

## Meaning first: a blocking pass

Read the message or conversation as something people would actually say. Explain what each person wants, what practical result the exchange achieves and why every reply follows from the previous turn. For an open task, explain why the learner would speak or write through this medium to this recipient. Use only stated context. If a rationale needs an invented off-page event, instrument, relationship or motive, mark it revise or reject.

Check object categories, pronoun referents, cause and effect, time and place, practical purpose and the link between picture and text. Flag unexplained topic jumps, stocktaking, repeated pairs or triples and dialogue that recites possible answer choices. A funny visible object is allowed; it does not excuse incoherent surrounding communication. Do not rescue a weak source by calling it beginner language, creative humour or a classroom game. Require a concrete reason in the source. Ordinary choices are allowed when they serve the interaction, such as a waiter offering three kinds of soup. Do not mechanically reject every list or unusual object; explain the actual mismatch or lack of purpose.

Write source-specific evidence. A repeated statement such as “the prompt and pictured event support this task” does not explain the scene. Identify the actual objects, actions and context that make each item coherent, along with any remaining risk. The gate rejects exact duplicate summaries, purposes or contrivance checks within a batch; the coordinator still evaluates their substance.

The rejected broom dialogue is a regression case: a speaker asks to turn music on; the reply offers radio, guitar or piano; the next turns inventory chairs, plates and glasses. It changes from a device to instruments without establishing live performance, then supplies unrelated stock solely for distractors. A literal answer quote and balanced keys cannot make it pass. Also reject a task that asks someone to text the person shown beside them about facts that person already sees, unless the prompt establishes a reason for that message.

Persist item-specific findings before opening the answer material. Then read the complete batch, starters and author notes, examine every question and audit the rest of the rubric. Distractors are derived from a coherent source. They must never dictate extra dialogue or unrelated facts. Familiar alternatives need not all be mentioned in a short A1 source when the question asks for an explicitly stated fact.

Classify each source independently as `meaning.tone: "ordinary"` or `"light-humor"`. Most tasks must use ordinary everyday scenes. The user wants around 15% lightly funny tasks across the program: five of the current 36 A1 items. A pleasant graphic style, a pet or a paper café decoration does not by itself make a scene strange. Record `tone_balance: {ordinary, light_humor, target_share: 0.15, scope_note}` with exact counts and the batch's contribution to the full program. The gate allows rounding up for a small batch; the coordinator must still check the combined count. Reject a batch that treats every exercise as an absurd scene.

After repairs, repeat the meaning pass on the final source. Rebuild the blind packet from those bytes. Record `review_contract_version: 2` and `meaning_first: {verdict: "pass", review_order: "source-before-questions", packet_sha256, independence_note}`. Each item needs `meaning: {verdict, coherence_rating, situation_summary, communicative_purpose, contrivance_check, unsupported_assumptions}`. Only ratings 4 or 5 can pass; these are editorial judgments, not validated difficulty. Passing items have no unresolved unsupported assumptions. Listening also records `turn_links`, one entry per exact script turn with its one-based `turn`, verbatim `quote` and specific `response_function`. For B1 question fragments, number all turns consecutively across fragments and include `fragment: question.id` on each turn link. The blind packet preserves these scripts under `fragments` without their questions or options. Open tasks add `medium_and_recipient_check`. A schema-complete report does not prove sound judgment; the coordinator reads these explanations before adoption.

In the full-item pass, inspect everything the learner sees before answering, including the title, situation, image alt and every optional starter. A speaking title such as “Een grote beker” supplies both picture-description goals; a later starter that names the cup also leaks the earlier object goal. Use a neutral title and starters that do not complete another criterion. Descriptive alt text is an accessibility replacement for the picture, not a visible caption: open picture tasks must retain equivalent pictured facts in their alts. Do not hide those facts from screen-reader users. Closed-task alts must avoid giving away listening or reading keys.

Read all printed questions together. A later question such as “Waar ligt haar pen?” gives away an earlier “Wat zoekt ze?” answer. The source may be coherent while the question pair still fails. Check every closed question against the other prompts, titles and visible cues, then repair the tested fact or wording rather than adding unrelated source details.

Now read `docs/briefs/author.md`, the part's verified exam description when applicable, all full source fields and notes, and the same part in the catalogue for diversity. A1 uses the foundation practice target and has no official-exam comparison.

Check per item: the rubric's fifteen points; for closed items prove each key from the verbatim evidence, test each distractor against the text (anchored, plausible, clearly false; no key that is the longest, most specific or the odd polarity out; no prompt word that recurs only in the key), paraphrase between question and text, the purpose/opinion/inference mix the part requires; for open tasks the required instruction form in the prompt, criteria that cover exactly what the prompt asks (a learner who does what the prompt says must meet every criterion), one null quote per sample, verbatim quotes, the model's length and level, starters aligned with the criteria; for scripts spoken naturalness and TTS-safe numbers; for pictures cast traits verbatim, one clear action, sequences consistent, pairs differing only in the point asked; invented names checked on the web. Level: apply the §10 heuristics per text or model. A2 and B1 receive an easier / comparable / harder verdict against the relevant official item, with a flag when off-level. A1 is checked against the foundation authoring target in §4.0, without an official-exam comparison.

Then repair rather than request: write `content/batches/<NNN>-proposed.json` — the batch with every required and recommended edit applied (exact wording, derived fields rebuilt: listening `text` from scripts, quotes verbatim, starters in step with criteria) — and `content/batches/<NNN>-proposed-starters.json` when a criterion or starter changed. Run `npm run batch:check` on the proposed file; it must end with no failures. An item whose premise, answer logic or task design cannot be repaired locally is rejected: remove it from the proposed file and say why.

Write `content/reviews/<NNN>-review.md` — short: a table (id, verdict, level verdict, one-line reason), the list of edits you made (field → new text, why), rejected items, diversity and set-assembly notes, media notes (voice pairing, picture risks), limitations — and `content/reviews/<NNN>-review.json` with `review_id`, `source: "content/batches/<NNN>-original.json"`, `source_sha256` = the SHA-256 of the PROPOSED batch file (the bytes that will be adopted), `starters_source`/`starters_sha256` (of the proposed starters when you changed them, else of the author's file) and `starters_verdict` for open tasks, `review_type`, `rubric`, `reviewed_at`, `batch_verdict` ("pass" when every item in the proposed file passes), `ready_for_integration: true` in that case, `edits` (the list), `rejected`, `checks`, `items` (per id: verdict, level, evidence). The coordinator adopts the proposed files with `npm run batch:adopt <NNN>`, which verifies your hash.

Do not edit the author's batch, starters or notes, the catalogue, config or app code. Report in a few lines: pass/edited/rejected counts, the edits, level flags, the proposed file's hash, anything the coordinator must do.

## Contract and replacements

Run the shared batch checker on the exact proposed source after the last edit. Inspect `taskType`, domain and B1 `textType` in the full exercise context; having a recognised tag does not prove the tag fits. Reject the retired `type` field. For a replacement batch, record `replaces` as the array of exercise IDs intentionally superseded, preserve every supplied ID and verify the complete rewritten exercises. Integration verifies each item has a passing review and reruns the authoring contract before accepting the batch. The catalogue replaces obsolete fields; media must be regenerated whenever the text it represents changed.
